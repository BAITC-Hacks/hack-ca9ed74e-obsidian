# Firebird — умный подбор event-подрядчиков

**Команда Obsidian · HackAlem 2026 · трек «Торговля» · задача #79-lite**

Firebird помогает заказчику выбрать до трёх подходящих подрядчиков из уже открытого каталога, а не расширяет поиск бесконечным списком. Пользователь задаёт город, дату, формат события, категорию и бюджет; при необходимости — длительность и язык. Сервис отсекает неподходящих и занятых кандидатов, возвращает стабильную выдачу и показывает проверяемую причину выбора для каждой карточки.

> Проект не бронирует услуги и не отправляет заявки. Его задача — сделать первый выбор подрядчика объяснимым и быстрым.

## Почему это ценно

В event-каталоге можно найти десятки похожих профилей, но заказчику трудно понять, кого выбрать и почему. Firebird превращает условия заказа в прозрачный короткий список:

- не предлагает подрядчика, занятого в указанную дату;
- честно учитывает бюджет, формат, язык и длительность;
- объясняет каждую рекомендацию фактами из каталога, а не общей фразой;
- отличает отсутствие категории в городе от слишком строгих условий;
- при пустом результате называет причины отказа и предлагает осмысленно смягчить запрос.

Это снижает риск ручной ошибки и даёт пользователю основание доверять выдаче: он видит и правило, и исходный фрагмент описания, на который опирается рекомендация.

## Что реализовано

- Web-интерфейс с формой заказа и шестью готовыми демо-сценариями.
- Подбор не более трёх подрядчиков из каталога по городу, категории, дате, формату, бюджету, языку и длительности.
- Проверка календаря занятости для всех категорий, включая банкетные залы.
- Три явных состояния: **подобрали**, **категории нет в городе**, **кандидаты есть, но ни один не прошёл условия**.
- Счётчики причин отказа и безопасные контрфактические подсказки: другая дата, достаточный бюджет, снятие требования к языку или длительности.
- Детерминированный порядок: один и тот же запрос возвращает одинаковые карточки даже при изменении порядка строк CSV.
- Карточка с ценой «от», городом, категорией, признаками исходных данных и индивидуальным объяснением.
- HTTP API, валидация запросов, production-сборка и автоматические тесты.

## Как работает подбор

```text
React-интерфейс
      │ POST /api/recommend
      ▼
Node.js HTTP API ── Zod-валидация запроса
      │
      ▼
CSV-каталог в памяти
      │  1. город + категория
      │  2. исключение: занятость / бюджет / формат / язык / длительность
      │  3. ранжирование: релевантность описания → цена → ID
      ▼
До 3 карточек + доказательное объяснение + причины пустого результата
```

При старте сервер читает `data/catalog.csv` в память; база данных и учётная запись не требуются. Вход проверяется через Zod, поэтому API принимает только корректную дату в окне календаря, положительный бюджет и значения из каталога.

### Правила отбора и порядка

1. Берутся только профили с точным совпадением города и категории.
2. Профиль исключается, если он занят в дату, его стартовая цена выше бюджета, он не берёт формат, не работает на запрошенном языке или его `max_hours` меньше нужной длительности. Для профилей без ограничения присутствия `max_hours = null` длительность не ограничивает выдачу.
3. У оставшихся профилей ищутся конкретные предложения в `description`, связанные с форматом события. Совпадения терминов формата дают приоритет; далее применяются стартовая цена и `id`. Поэтому результат стабилен и не зависит от порядка CSV.
4. Показываются первые три кандидата. Если их меньше трёх, интерфейс прямо указывает фактическое число.

### Объяснимость и AI

По умолчанию Firebird работает целиком локально. Каждое объяснение содержит факты, уже прошедшие фильтры: отсутствие отметки о занятости на дату, формат, цену относительно бюджета, а при наличии — язык и длительность. В конце выводится буквальный фрагмент описания профиля.

В коде есть **необязательный** адаптер совместимого с Chat Completions AI API. Он не создаёт рекомендации, не меняет порядок и не придумывает факты: из заранее подготовленных фрагментов он может выбрать только один наиболее уместный `evidence_id` для каждой уже выбранной карточки. Ответ проходит строгую проверку; при тайм-ауте, ошибке или некорректном ответе сервис автоматически использует локальное объяснение. Основной сценарий и все проверки работают без AI-ключа.

Такой подход сочетает смысловую помощь AI с контролируемой, воспроизводимой логикой: модель не становится непрозрачным ранжировщиком и не может выдать неподтверждённую причину.

## Данные и внешние компоненты

- Каталог организатора находится в [`hack-ca9ed74e-obsidian/firebird/data/catalog.csv`](hack-ca9ed74e-obsidian/firebird/data/catalog.csv): 66 анонимизированных профилей, из них 13 помечены в исходных данных как `synthetic`. Флаги `synthetic`, `city_imputed` и `price_imputed` сохраняются при загрузке; в карточках заметен признак `synthetic`.
- Проект не добавляет скрытые данные, не обучает модель на каталоге и не передаёт каталог внешнему сервису в локальном режиме.
- Открытые npm-зависимости: TypeScript, React, Vite, Node.js, Zod, `csv-parse`, `dotenv`, Vitest и `lucide-react`. Их точные версии зафиксированы в `pnpm-lock.yaml`.
- Внешний AI API — опциональный компонент, включаемый только переменными окружения ниже. Для технической проверки он не нужен; ключи и персональные аккаунты не требуются.

## Быстрый запуск

### Требования

- Node.js **22.13.0 или новее**;
- pnpm **11.25.0** (версия зафиксирована в `package.json`);
- доступ к репозиторию и интернет только на момент первой установки npm-зависимостей.

Личный аккаунт, платная подписка, база данных или API-ключ **не нужны**.

### Установка

В корне клонированного репозитория выполните:

```sh
cd hack-ca9ed74e-obsidian/firebird
corepack enable
corepack pnpm install --frozen-lockfile
```

`corepack` поставляется с поддерживаемыми версиями Node.js и использует версию pnpm, указанную в проекте. Если Corepack отключён в вашей среде, установите pnpm 11.25.0 привычным для вашей ОС способом и выполните `pnpm install --frozen-lockfile`.

### Проверка и production-запуск

```sh
pnpm check
pnpm build
pnpm start
```

## Основной сценарий проверки

Проверяющий может выполнить всё через интерфейс, не создавая учётную запись.

| Сценарий | Параметры | Что должно быть видно |
| --- | --- | --- |
| Плотная категория | Алматы · Ведущий · корпоратив · 10.10.2026 · 1 000 000 ₸ · 6 ч · русский | Три карточки из четырёх подходящих; у каждой своё объяснение и источник из описания. |
| Та же заявка, другая дата | Нажмите «Другая дата» — 17.10.2026 | Состав карточек меняется только из-за календаря; в объяснениях новая дата. |
| Редкая категория | Алматы · Флорист · свадьба · 10.10.2026 · 300 000 ₸ | Показано меньше трёх карточек и честное число найденных кандидатов. |
| Категории нет | Астана · Декоратор | Отдельное сообщение: в городе нет такой категории. |
| Кандидаты есть, но условия не подходят | Алматы · Ведущий · корпоратив · 10.10.2026 · 100 000 ₸ · 6 ч · русский | Пустой результат с числом отказов по причинам и полезной подсказкой по бюджету. |
| Пиковая занятость | Пресет «Декабрьский пик» | Видно, что пустая выдача связана с занятостью, а не с ошибкой интерфейса. |

Повторите любой из запросов: порядок карточек не изменится. Измените только дату в первом сценарии — выдача изменится согласно `busy_dates`, а не случайно.

## API для независимой проверки

| Метод и маршрут | Результат |
| --- | --- |
| `GET /api/health` | Статус сервера и число загруженных профилей |
| `GET /api/catalog` | Допустимые значения фильтров, границы календаря, метаданные каталога |
| `POST /api/recommend` | Подбор, причины исключения, подсказки и карточки |

Пример тела запроса:

```json
{
  "city": "Алматы",
  "date": "2026-10-10",
  "format": "корпоратив",
  "category": "Ведущий",
  "budget": 1000000,
  "hours": 6,
  "language": "русский"
}
```

Успешный ответ содержит `status: "matched"`, `eligibleCount`, не более трёх `recommendations`, `reasons`, `suggestions`, режим объяснения и `elapsedMs`. Возможные `status`: `matched`, `category_absent`, `no_match`.

## Проверки качества

Набор Vitest-проверок покрывает:

- загрузку всех 66 записей и сохранение признаков происхождения;
- календарь на всём 100-дневном окне, включая декабрьскую плотность;
- точные границы бюджета и длительности, язык, формат и занятость;
- отсутствие дубликатов в категориях с несколькими услугами;
- три пользовательских состояния и контрфактические подсказки;
- детерминизм при повторном запуске и перестановке строк каталога;
- API, ошибки валидации, работу без AI и безопасный fallback AI-адаптера.

На актуальной версии проекта `pnpm check` проходит: **3 test files, 31 tests passed**; `pnpm build` успешно собирает production-клиент.

## Потенциал развития

Сейчас Firebird — прозрачный слой выбора поверх статического каталога. Для площадки-агрегатора он может развиться без замены ядра:

- подключать реальные календари и обновления цен из кабинетов подрядчиков;
- учитывать дополнительные фильтры: вместимость, район, тип площадки, рейтинг и доступность команды;
- хранить обратную связь о том, какие объяснения и карточки действительно помогли выбрать;
- масштабироваться на новые города, категории и другие вертикали услуг, сохраняя доказательные причины выбора;
- добавлять LLM-помощника только в ограниченной роли интерпретации проверяемых данных, оставляя фильтры и порядок аудируемыми.
